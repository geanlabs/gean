# Gean: Lean Ethereum consensus client

An open-source Lean Ethereum consensus client, written in Go and maintained by Gean Labs.

![Gean banner](docs/assets/gean-banner.png)

## Overview

Gean is:

- A consensus client for [Lean Ethereum](https://github.com/leanEthereum), designed for fast finality, quantum-resistant security, and a simpler core protocol.
- Implementing Lean Consensus devnet-5 alongside independent client implementations.
- Built for clarity and auditability, with a deliberately small codebase.
- Quantum-resistant by design, using XMSS signatures instead of BLS signatures.

## Getting started

### Prerequisites

- [Go](https://go.dev/doc/install) 1.25+
- [Rust](https://www.rust-lang.org/tools/install) 1.92.0
- [uv](https://docs.astral.sh/uv/)
- [Docker](https://www.docker.com/get-started/)

### Building and testing

```sh
make build       # Build the Rust FFI and Go binaries
make test        # Run Go unit tests
make test-ffi    # Run XMSS FFI tests
make test-spec   # Generate and run production-scheme consensus fixtures
make lint        # Run Go and Rust linters
make docker-build
```

Run `make help` for all available targets.

### Running locally

For a multi-client devnet:

```sh
make run-devnet
```

For a three-node Gean network, run the setup once and start each node in a separate terminal:

```sh
make run-setup
make run
make run-node1
make run-node2
```

At least one node must run as an aggregator for the network to finalize.

### Prover threads

Use `--prover-threads 8` to start with eight Rust backend pool threads, including
its calling thread. The default, `0`, uses the CPUs available to the process.
On a shared host, a smaller pool can reduce CPU contention; measure aggregation,
block proposals and finality before choosing a value.

The setting applies before any XMSS work and is fixed until restart. It also
applies to other work using the shared Rust backend pool. It does not change
Go's `GOMAXPROCS`, pin CPUs or reserve cores. Values above the available CPU count
fail startup. Check the `prover pool threads: 8 (including caller)` startup log.
In Docker, pass the flag as a Gean argument; a CPU quota alone does not resize an
already initialized pool.

### Memory requirements

Block-proposal and aggregation proofs are generated by the XMSS prover, which
adds a transient multi-gigabyte peak per proof. By default gean proves on the
system allocator, so that scratch is freed after each proof and a long-lived
node's memory stays bounded — this is the mode for packing many nodes onto one
host (interop devnets). `--prover-arena` instead proves on leanVM's bump arena:
faster, but the arena never returns pages, so RSS ratchets to the allocation
high-water mark (~12 GB) and stays there — use it only on a host with memory to
spare where proving latency is the constraint.

Either way, a proof's transient peak is multi-gigabyte; tighter container limits
get the process OOM-killed mid-proving, which is silent in the application log
(check `docker inspect` for `OOMKilled` or the kernel log). The image sets
`GOMEMLIMIT=2GiB` to keep the Go heap out of the prover's headroom; override it
via the environment if your budget differs.

## Philosophy

Gean treats reviewability as a consensus-safety property. Consensus-critical behavior should remain small enough to audit end to end, and disagreements between clients should be traceable to a small number of files.
